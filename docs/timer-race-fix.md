# Общий clock и потерянный сигнал таймера

Исследование 2026-10-15, живой зависший PID 9384, диагностическая сборка
expanded-v2. Артефакты перечислены в music-autosave-investigation.md.

## Установленная цепочка зависания сохранения

1. Запрос type=5, object `0x2D7288`, state `0x2D7294=0x4F`, substate
   `0x2D7298=0x4F`. XBE jump tables ведут к `sub_0019B420`, ветке
   `loc_0019B72A`. Перед дальнейшим шагом она ожидает внутреннюю задержку.
2. `0x2D7158=1` (delay active), `0x2D715C=0` (accumulated),
   `0x2D7160=0xBB8` (3000 ms), `0x2D7164=3`.
   Эти значения совпали в двух чтениях, разделённых минутами.
3. Update `sub_00197660` прибавляет полученный delta к `0x2D715C`.
   Проверенный live breakpoint сработал; caller на guest stack `0x0002DD86`,
   переданный delta=0. Соединение после чтения успешно detached.
4. В caller `sub_0002DD30` delta вычисляется как
   `sub_001940A0() * 1000 / sub_001940C0()`.
   Первая функция читает `0x2D6C44 - 0x2D6C14`, затем сохраняет текущий tick
   в `0x2D6C14`. Вторая возвращает frequency `0x2D6C40`.
5. В памяти frequency=100; current/previous tick одинаковы: `0x7B52`.
   Этот clock обновляет `sub_001938A0`, который в native-стеке стоит
   в ожидании события `48000001`. Поток обслуживания multimedia timers
   `sub_001BBF39` также ждёт, хотя UI и audio-update продолжают работать.

Таким образом подготовка сохранения ждёт задержку, время для которой не
растёт. Это наблюдённый механизм; первичная остановка clock расследуется
отдельно. Связь этого общего clock с прекращением музыки согласуется с
симптомами; прямую причинную связь с музыкой пока не установили.

## Конкретный дефект runtime

В прежнем `kernel_set_timer`:

```text
lock timer table
publish armed timer
unlock timer table
ResetEvent(timer event)
```

Поток expiry мог между publish и ResetEvent удалить one-shot entry и
выполнить SetEvent. Поздний ResetEvent затем стирал готовый сигнал.
Дальнейшего expiry для one-shot уже нет, waiter остаётся заблокированным.

В живом снимке clock timer `0x01181D44` имеет callback `0x00193920`,
active byte=1, generation `0x7B54`. Generation ожидаемого timer ID совпадает.
Guest SignalState=1, host event signaled=0; запись этого таймера в активной
таблице уже отсутствует. Это совместимо с потерей сигнала. Сам по себе
разрыв guest/host state не доказывает конкретное interleaving: shadow waits
потребляют host auto-reset signal, guest SignalState при этом может оставаться
старым. Поэтому доказательство дефекта получено отдельным регрессионным тестом,
а доказательство, что именно он вызвал данный live-сбой, требует нового прогона.

## Исправление и тест

`kernel_bridge.c`: сброс старого события и guest SignalState выполнен под
`g_timer_lock` перед публикацией. Обработка expiry, её dispatcher state и
SetEvent защищены той же блокировкой. DPC выполняется после release lock,
так как callback может rearm/cancel timer. Это также исключает поздний
SetEvent от expiry после уже выполненного rearm в этом критическом участке.

`tests/kernel_timer_signal.c` вызывает настоящие runtime arm/expiry helpers.
ResetEvent перехватывается тестом, чтобы поток expiry гарантированно попытался
выполниться в опасном месте. При прежнем порядке ResetEvent после publish:
`expiry signal after concurrent arm: LOST`, тест падает. При исправленном:
`PRESENT`, PASS. Дополнительно проверены сброс при rearm и periodic expiry/DPC.

Старый порядок воспроизведён во временной копии текущего runtime с возвратом
именно arm-order; исходная производственная функция expiry тестируется в обоих
вариантах. Это не аппаратный тест и не проверка музыки на слух.

## Артефакты сборки

Финальная Android сборка успешна. APK и unstripped symbols:
`build/diagnostics/timer-fix-v1/`, рядом SHA256SUMS.
В логе запуска появляется `timer arm/expiry signals serialized (timer fix v1)`.
Расширенная диагностика и previous-log сохранены.

После установки исправления пользователь 2026-10-15 подтвердил полный прогон
турнира: музыка не пропадала, автосохранение завершилось нормально. Это один
успешный прогон на устройстве, а не доказательство окончательного устранения
случайного сбоя. Нужны повторные длинные прогоны. Ранее пойманный вылет в
DirectSound остаётся отдельно не объяснённым.
