# Пропадание музыки и зависание после гонки

Дата исследования: 2026-10-14. Исследован текущий checkout и лог подключённого
устройства. Исправления поведения не внесены; случай со сбоями не воспроизведён.
Тестировщик сообщил: после пропадания музыки зависание на автосохранении
наблюдается в 100% таких случаев. Число проверенных случаев неизвестно.

## Основная гипотеза

Звуковой worker перестаёт обслуживать аудио во время гонки. При выходе из гонки
игра пытается выключить аудиосистему и ждёт этот же worker без ограничения
времени. Экран автосохранения может быть последним отображённым экраном,
а фактическое ожидание может происходить при остановке звука.
Это объяснение согласуется с кодом, но не установлено как причина наблюдаемого сбоя.

## Подтверждено статическим исследованием

Адреса относятся к Xbox guest, не к адресному пространству Android.
Источники: `android/app/build/generated/recomp/recomp_0037.c` и исходный
runtime в `xboxrecomp/src/kernel/`.

- Инициализация аудио устанавливает байты `0x002DDCEC` и `0x002DDCED` в 1.
- Аудиопоток `sub_001A5C60` выполняет цикл, пока `0x002DDCED != 0`.
  В цикле вызываются `sub_001A2760`, `sub_001A2720`, `sub_001A5B30`,
  `sub_001A8860` и callbacks через `0x0025E69C`, `0x002DDCC4`,
  `0x002DDCC8`, `0x0025E6A0`. Выход из цикла сбрасывает `0x002DDCEC` в 0
  (`loc_001A5D1E`).
- Выключение `sub_001A6110` сбрасывает `0x002DDCED` в 0 и повторяет
  `sub_00164605(0)`, пока `0x002DDCEC != 0` (`loc_001A6120`). Таймаута нет.
  Каждый проход заново читает флаг: это не случай загрузки флага один раз
  перед циклом.
- `sub_001A3980` вызывает `sub_001A6110` при очистке аудиосистемы.
  Попадание перехода после конкретной гонки в эту функцию ещё не измерено.
- Guest-потоки сериализуются GIL. Kernel-вызовы обычно отпускают его;
  сами kernel-вызовы времени и IRQL могут удерживать его. Поэтому наличие
  потоков в `gil_lock` само по себе не доказывает deadlock.

## Другие обнаруженные кандидаты

Они требуют проверки на пути конкретного сбоя, а не исправления наугад.

1. `kernel_file.c`: чтение с явным смещением использует `lseek` + `read`
   отдельными операциями. Если один fd читают одновременно несколько потоков,
   возможна гонка позиции. В текущем логе большинство чтений последовательные;
   одновременный доступ к одному музыкальному fd не установлен.
2. `kernel_bridge.c`: file APC доставляется немедленно внутри bridge,
   а не отложенно при alertable wait. Это допускает повторный вход в код
   вызывающего потока. Наличие APC на проблемном музыкальном запросе неизвестно.
3. Общие guest critical sections и DirectSound/IRQL: worker может застрять
   внутри вызова до проверки stop-флага. Нужны стек worker и владелец его lock.
4. Отдельная неисправность записи сохранения пока также не исключена:
   необходимы стек главного потока и фактический результат `NtWriteFile`.

## Как подтвердить механизм

Не перезапускать игру между двумя точками: лог открывается с режимом `w`.

1. Пока музыка играет, сохранить лог и снимок всех native-потоков.
2. Сразу после исчезновения музыки, до завершения гонки, повторить снимок.
   Найти worker с `sub_001A5C60` и определить, выполняет ли он цикл,
   ожидает lock/event/I/O или уже завершился.
3. На зависшем экране автосохранения сделать ещё два снимка с интервалом
   несколько секунд. Проверить главный поток на `sub_001A6110` /
   `loc_001A6120`, worker и байты `0x002DDCEC`, `0x002DDCED`.
4. Главный поток в этом цикле, `CEC=1`, `CED=0` и worker, застрявший в том же
   месте ещё до окончания гонки, подтвердят связь через остановку аудио.
   Если главный поток ждёт запись файла, расследовать этот путь отдельно.
5. Исправлять первичную остановку worker. Принудительное обнуление `CEC`
   или таймаут с продолжением очистки могут освободить ресурсы живого потока
   и скрыть причину.

Безопасное чтение лога с Linux:

```bash
adb devices
adb shell pidof org.nfsu.android
adb pull /sdcard/Android/data/org.nfsu.android/files/nfsu1.log /tmp/nfsu1-before-finish.log
```

Для native-стеков требуется debugger attach с библиотекой и символами именно
установленного APK. Адреса от другого запуска или другой сборки не подходят.

## Диагностическая сборка

Добавлен `[AUDTRACE]`: каждые 5 секунд SDL host-поток печатает снимки
аудиопотока и вызывающего остановку аудио потока. Guest-код не прерывается
сигналом и debugger не нужен. Никакого таймаута очистки или обхода ожидания нет.

- `ticks` растёт при входе в аудио-update `sub_001A2760`.
- `function` — последняя обёрнутая функция; `kernel` — ordinal потенциально
  блокирующего kernel-вызова, пока bridge не вернулся; `caller` — его guest site.
- `age_ms` — время с последней записанной границы.
- `sampled_active`, `sampled_run` — флаги, прочитанные при последней границе
  guest-функции, а не live-чтение из потока наблюдения.
- `stack_words` — до 16 слов собственного guest-стека на последней границе;
  это сырой контекст (включает аргументы), не развёрнутый native backtrace.
- `shutdown entered` / `shutdown returned` показывают, вернулась ли остановка.

Неизменный `ticks` несколько снимков подряд локализует остановку update.
Постоянный `kernel` с растущим `age_ms` указывает на невозвратившийся bridge.
`kernel=0` не исключает ожидание GIL после возврата из ядра или зависание
внутри guest-кода. Для этого снимок даёт последнюю границу и stack_words.

После исчезновения музыки сохранить лог до окончания гонки, затем ещё один
при зависании. Не перезапускать игру до копирования обоих логов.

Проверки реализации: `:app:assembleDebug --offline` завершилась успешно;
генератор создал все три тела `_gen`, `git diff --check` без замечаний.
Проверка сборки не доказывает воспроизведение сбоя или правильность звука.

## Присланный лог `/home/pavel/Downloads/nfsu1.log`

Пользователь уточнил: вылет произошёл ещё во время гонки.
Это отдельный наблюдаемый результат; ожидание автосохранения в этом прогоне
не зафиксировано.

- В конце лог содержит SIGSEGV (signal 11), guest fault VA `0xFFFFFFBE`.
- Raw guest stack содержит `0x001E5470`, `0x001E58A1`, `0x001E593E`,
  `0x001E5A54`, `0x001E5AD1`. В текущем generated code это последовательность
  вызовов DirectSound `sub_001E5A2C -> sub_001E590F -> sub_001E588E ->
  sub_001E5423 -> sub_001E6921`.
- `sub_001E5423` проверяет состояние voice и вызывает `sub_001E6921`,
  когда связанный список не пуст. В `sub_001E6921` есть извлечение объекта
  из list-node вычитанием `0x4C`, затем чтение voice index по смещению `0xA`.
  Нулевой list-node в таком пути даёт адрес `-0x4C + 0xA = 0xFFFFFFBE`,
  совпадающий с fault VA. Это конкретный кандидат на повреждённый/неверный
  список; точный faulting PC в этом логе отсутствует, поэтому конкретная
  инструкция и источник повреждения ещё не доказаны.
- Все 78 снимков worker показывают рост `ticks`; к последнему он равен
  39171. Длительного зависания update по этим снимкам нет (интервал 5 s).
  Последний снимок: `kernel=99`, `age_ms=4`, обычный короткий sleep.
- Оба зарегистрированных `shutdown entered` имеют `shutdown returned`.
  Повторяемый `lane=shutdown running=0` — сохранённый результат прошлой
  остановки, а не текущее ожидание. Первая гипотеза о невозвратившемся
  shutdown не подтверждается этим прогоном.
- В строках `[READ]` нет ненулевого `st`; это не проверка правильности данных.

Дальнейшая локализация: проверить list-head и оба соседа непосредственно
перед извлечением voice в `sub_001E6921`, сопоставить с оригинальным x86 и
зафиксировать faulting native PC. Нельзя просто пропускать обработку нулевого
узла: это скроет первичную ошибку состояния voice/list.
